Layer 04 · Gateway: see the whole stackRunix Bench · Available

The open benchmark for LLM gateways

Runix Bench is an open method and a self-test for any OpenAI-compatible gateway or relay, measured from the outside the way your application sees it: price against the official list price, time to first token and throughput, success rate over 30 days, caching, and behavioural checks on whether the model is the one on the label. The probe and every raw result are public.

See the live leaderboard Run it on your gateway

Open source under the MIT licence. Measure, don't trust: the probe, the prompts and the data are in the repository, so a result can be checked rather than believed.

03 · Capabilities

Five questions, in the order they matter

A team picking a gateway asks whether it can trust it, then whether it is cheap, then whether it stays up. The benchmark answers in that order, and reads a low price next to trust: a gateway far under list price is a warning sign, not a bargain.

01

Trust and integrity

Is it the real model, and will the operator still be there? Behavioural checks test it from outside: whether the model names itself, handles tool calls and Chinese text, streams for real, and reports usage that matches a recount. Data retention and the legal entity are annotated with links to the source. A diff against the official API in the manner of the K2 Vendor Verifier is the method being built toward; no endpoint has passed one yet.

02

Price against list

The gateway's price divided by the official list price, per model and as one index across models. Cache pricing and hidden multipliers are recorded beside it.

03

Stability over 30 days

Success rate from scheduled probes, with rate limits, outages and timeouts counted apart. Errors the probe causes itself, such as an unauthorised key, are excluded and shown separately.

04

Speed

Time to first token at p50, and p95 only when a run has at least five samples. Throughput is decode speed, counted after the first token; llmperf and Artificial Analysis divide by the whole request, first token included, so their figures read lower. Fake streaming, a reply buffered and then dumped, is flagged.

05

Cache

Whether the second of two identical long prompts reports cached tokens in its usage block, measured rather than taken from the price page.

06

Ratings that need evidence

Channel origin is rated verified, claimed but unverified, or unverified, and nothing without an evidence link is ever marked verified. A related party is never rated a tier higher for the relationship.

04 · How it works

Where it sits, and how it measures

The benchmark stands where your application stands: outside the gateway, calling its public endpoint. It needs no access to anyone's infrastructure and no cooperation from the operator.

01

A public probe

The probe script and its prompts are in the repository. Each request carries a random id so a gateway cannot serve it from a cache, output is capped, and concurrency stays at four or under so a run never becomes a load test.

02

Scheduled, then committed

A job scheduled every six hours, which GitHub's scheduler currently delivers about twice a day, probes the endpoints it has keys for and commits each raw result. Leaderboard figures come from a rolling 30-day window; older runs stay in the data and do not move the table.

03

Agent runs on Terminal-Bench

Beyond single calls, our team runs Terminal-Bench tasks through Harbor on a fixed pair of test routers, Claude Code for Claude models and Codex for the rest, with A/A and A/B statistics. The reports keep verifier scores, cost and integrity checks, and copy no prompts.

04

What a figure compares

The price matrix and the self-test compare one tracked model across gateways, each under the name that gateway gives it. The scheduled probe runs a short model list per endpoint, so the leaderboard's speed and success figures describe a gateway, not one model on it.

05

Evidence for what is annotated

What a probe cannot measure, a data-retention policy or the legal entity behind a service, is annotated by hand, with a link to the source where one exists and the date it was read. Corrections are taken as pull requests.

06

Unknown stays unknown

A measurement that could not be taken is shown as missing, never as zero. The probe region is printed on every figure, and results from different regions are never mixed.

05 · Why open

Why a gateway company publishes a gateway benchmark

We sell a gateway, so a benchmark we run could be read as marketing. It is built so that it does not have to be trusted: the method is written down before the numbers, the raw data is public, and anyone can rerun it against the same endpoints with their own key. That is the same rule we hold our own products to.

08 · How to start

How to start

Runix Bench is self-serve. Nothing here needs an account with us.

01Read the table

Open the live leaderboard and sort by the dimension you care about. Each figure links to the run it came from.

02Test your own gateway

Clone the repository and run the self-test with your own key. It writes one report you can share.

03Suggest a gateway or a fix

Open an issue or a pull request on the repository to propose a gateway or correct an annotation. A gateway joins the live table once there is a key to probe it with.

09 · Questions

Common questions

What does Runix Bench measure?

Five things about an LLM gateway or relay, in the order they matter to the team that depends on it: whether it can be trusted (the model behind the endpoint, data retention, a legal entity), its price against the official list price, its success rate over 30 days, its speed (time to first token and throughput), and whether repeated prompts hit a cache.

Is it free?

Yes. The probe, the methodology and every raw result are open source under the MIT licence, and the self-test runs on your own machine with your own key. Managed probing and report hosting are described on the benchmark site.

Does my API key leave my machine?

No. The self-test runs locally and calls the gateway you point it at directly. The key is read from an environment variable and is not written to the report.

Is Runix Router in the table?

Not today. The one gateway measured live so far is run by a related party; it is marked as such on its row and rated by the same rules as everyone else, never a tier higher for the relationship.

How often is the table updated?

The job is scheduled every six hours, and GitHub's scheduler currently delivers about two runs a day; each run is committed to the repository. Success rates are computed over a rolling 30-day window, with the 7-day figure beside it.

Why would a gateway company publish a gateway benchmark?

Because a buyer should not have to trust any gateway's claims, including ours. The benchmark is built to be checked rather than believed: the prompts are in the script, the raw data is public and anyone can rerun it against the same endpoints with their own key.
