How to benchmark an LLM gateway before it carries production traffic

An LLM gateway sits on every model call an application makes, so its failures become the application's failures. Every gateway's own page says it is fast, cheap and reliable. A benchmark answers the question from where the application stands: outside the gateway, calling its public endpoint with an ordinary key. This guide sets out five checks in the order they matter, the order Runix Bench uses, and the red flag each one catches.

Check 1: is it the model on the label?

Trust comes first because every other number is meaningless if the model behind the endpoint is not the one being billed. The failure modes are quiet: a cheaper model served under a premium name, weights quantized until long or non-English answers degrade, a hidden system prompt that inflates every request, or a long context silently trimmed to save cost.

The way to check is a diff against the official API. Send the same fixed request set to the gateway and to the provider directly, with tool calls, long context and sampling-sensitive cases in it, and compare tool-call validity, token counts and the shape of the answers. The K2 Vendor Verifier does this for tool calls, comparing how often they trigger and whether their arguments match the schema. A prompt that costs more input tokens through the gateway than through the provider is the simplest evidence of an injected prefix. Rate the result in three tiers only: verified, claimed but unverified, or unverified, and never mark anything verified without the evidence attached.

Trust also covers the operator. Read the data-retention and training terms in the formal policy, not the home page slogan, and check that a legal entity stands behind the service and will issue an invoice. A relay with no entity and no invoice is a counterparty risk however good its numbers are today.

Check 2: divide the price by the list price

For each model, divide the gateway's input and output prices by the provider's own list prices, average the two ratios, and take the geometric mean across models for one index: under 1 is cheaper than list, over 1 is a markup. Keep the two raw columns beside the index, because a gateway can discount input and mark up output and the average hides it. How to read an LLM price list covers the units, and the Router models catalogue shows list prices with the page each came from.

Read a low price next to the trust result. A price far under half of list is often a sign of a resold or reverse-engineered channel. That is a rule of thumb rather than proof, and a reason to look harder rather than a bargain. Also record what the price page leaves out: top-up fees, cache pricing, and multipliers applied to some models only.

Check 3: stability over thirty days, errors sorted by kind

One afternoon of testing says little about a service that has to work at three in the morning. Probe on a schedule, every few hours, and compute the success rate over a rolling 30-day window with the 7-day figure beside it. Count rate limits, server errors and timeouts separately: a 429 is a capacity signal, a 5xx is an outage, a timeout is often a queue, and they call for different responses.

Be fair to the gateway as well. Errors the probe causes itself, an unauthorised key or a model the gateway never offered, are excluded from the denominator and shown on their own. Then look at time of day: divide the time to first token in the slowest hour by the fastest, and treat a ratio of two or more as peak-hour throttling. What happens when a provider fails describes what a gateway should do on its own bad hour.

Check 4: speed, first token then throughput

Measure time to first token on streaming requests and report the median. Report a p95 only when a run has at least five samples, since with three samples the p95 is just the maximum. Measure throughput as decode speed, dividing the tokens generated after the first token by the time spent after it. llmperf and Artificial Analysis divide by the whole request, first token included, so their figures read lower; say which convention a number uses before comparing two.

Keep the probe honest: put a random id in each prompt so nothing is served from a cache, cap the output length, and keep concurrency at four or under so the benchmark never turns into a load test. Watch for fake streaming, where the first token arrives together with most of the answer because the gateway buffered the whole reply and replayed it.

Check 5: measure the cache, do not read about it

Prompt caching can cut the cost of repeated context sharply, which matters for agents that resend the same history on every turn. Send the same long prompt twice and compare the usage block and the bill: a cache that is advertised but never reported, or reported but billed at full price, fails the check. As why an LLM bill does not match the price list argues, check the bill, not the page.

Run the checks on your own gateway

Four of the five checks run automatically in LLM Gateway Bench, the open-source project behind Runix Bench, released under the MIT licence. The trust check combines behavioural fingerprints with manually annotated terms, and does not yet include a diff against the official API. A job scheduled every six hours, delivered about twice a day in practice, probes the endpoints it has keys for and commits the raw results. The self-test runs the same probe against any OpenAI-compatible endpoint with your own key, which never leaves your machine, and sets your gateway beside the public baseline and the official list price.

Single calls do not show what a gateway changes for an agent. For that, run the same Terminal-Bench tasks through two routers with the same agent, run the baseline twice to see the noise, and compare verifier scores and cost. A difference smaller than the gap between two runs of the same router is not a difference. What is an LLM gateway explains what the layer is for in the first place.

Questions this raises

What should an LLM gateway benchmark measure first?

Trust: whether the model behind the endpoint is the one being billed, checked by sending the same requests to the gateway and to the official API and comparing the answers and token counts. Price, uptime and speed only mean something once that holds.

How long should a gateway be probed before judging its uptime?

Thirty days, on a schedule of every few hours, with the 7-day figure beside it. Rate limits, server errors and timeouts are counted separately, and errors the probe causes itself are excluded.

Is a gateway that is far cheaper than list price a good deal?

Not on its own. A price under half of the provider's list price is often a sign of a resold or reverse-engineered channel. It is a rule of thumb, not proof, so read it together with the trust check.
