JuiceFS, Alluxio, Mountpoint and Runix FS: a file layer for AI data

Training data, checkpoints and model weights live in object storage because it is cheap and durable. Training code, inference servers and agents expect files. Something has to sit between the two, and the open-source options differ less in speed than in what they do to your bucket and where they keep the cache. This post compares four of them on those two questions: JuiceFS, Alluxio, Mountpoint for Amazon S3 and Runix FS, which is built on the Curvine project. It describes each project's documented design, not a benchmark run.

The first question: is the bucket still a copy of your files?

Some layers keep one object per file, so the path train/0001.parquet in the mount is the key train/0001.parquet in the bucket, and any other tool can still read the bucket directly. Others store file data in their own format and keep the directory tree in a separate metadata service, which buys full file-system semantics at the cost of the bucket no longer being readable on its own. Neither is wrong. The choice decides whether the file layer is a cache you can remove or a storage system you depend on, and why object storage is not a file system explains what each side gives up.

JuiceFS: a full file system that owns its layout

JuiceFS splits each file into chunks and blocks and writes the blocks to the bucket, while the directory tree, names and attributes live in a metadata engine such as Redis, MySQL, PostgreSQL or TiKV. The result is close to full POSIX: renames are cheap metadata operations, small writes and random edits work, and clients cache blocks on local disk.

The trade-off is the layout. The objects in the bucket are blocks, not your files, so reading the data without JuiceFS is not possible and the metadata engine becomes part of what has to stay up and be backed up. For a team that wants a general-purpose shared file system on cheap storage, that is a fair price. For a team whose bucket is also read by Spark jobs, data vendors or other tools, it is a migration.

Mountpoint for Amazon S3: a fast client that keeps S3 semantics

Mountpoint for Amazon S3 is an open-source FUSE client from AWS that maps files to objects one to one. It is deliberately narrow: it implements the operations object storage does well, reading, listing and writing new files sequentially, and its semantics document lists what it does not do, such as editing an existing file in place or most renames.

That makes it a good fit for read-heavy jobs on large files, and the bucket stays exactly as it was. It caches on the local disk of the machine that mounts it, so ten training nodes reading the same dataset each fetch it from the bucket and each keep their own copy. When the working set is shared across many nodes, the bottleneck stays where it was.

Alluxio: a distributed cache over the store you have

Alluxio places a cluster of workers between compute and the under-store and caches data on memory, SSD and HDD tiers, keeping the namespace of the bucket underneath. Applications reach it through a FUSE mount, a Hadoop-compatible client or its own APIs. Because the cache is shared, one node's read warms the data for the others, which is what a multi-node training job wants from a cache, and a multi-tier cache for AI training data covers how to size one. The project is written in Java and has open-source and commercial editions.

Runix FS: Curvine's cache, with two mount modes

Runix FS is built on Curvine, an open-source distributed file system and cache written in Rust, released under Apache 2.0 and accepted as a CNCF Sandbox project. Masters replicated with Raft hold the metadata, and workers cache data on memory, SSD and HDD tiers, so a working set read by one node is served to the others from the cluster. Applications reach it through a FUSE mount, a Hadoop-compatible client, Java, Python and Rust SDKs, or a Kubernetes CSI driver.

The difference is that each mount picks how writes reach the bucket. In cache mode the bucket is the source of truth, paths map one to one to object keys, and writes pass through, so the bucket stays readable by everything else. In file-system mode, operations complete in the cluster first and are synchronised to the bucket in the background, which suits write-heavy work such as checkpoints at the price of eventual consistency. When the bucket is the truth works through the choice. Runix deploys it in your own cloud account and supports it under contract.

How to choose

  • One node, large files, mostly reads: a client such as Mountpoint is often enough, and it adds nothing to operate.
  • Many nodes reading the same data: a shared, distributed cache, Alluxio or Runix FS, so the bucket is read once rather than once per node.
  • The bucket is shared with other tools: keep one object per file, which rules out layers that own the layout.
  • A general-purpose file system with heavy renames and small edits: JuiceFS, or Runix FS in file-system mode for the paths that need it.

What to test before you decide

Run your own workload, not a synthetic one: list and open a directory of many small files, because the small-files problem is where most layers differ; read a full epoch twice and compare the second pass; write and rename a checkpoint; and stop one cache node during a read to see what the job does. The Runix FS quick start mounts an existing bucket in three commands, which is enough to run all four tests against your own data.

Questions this raises

What is the main difference between JuiceFS and Alluxio?

JuiceFS is a file system that stores file data in its own block format in the bucket and keeps the directory tree in a separate metadata engine. Alluxio is a distributed cache that keeps the namespace of the store underneath, so the bucket stays readable without it.

Is Mountpoint for Amazon S3 a file system?

It is a FUSE client that maps files to objects one to one and implements the operations object storage does well. It does not support editing existing files in place or most renames, and it caches per machine rather than across a cluster.

Does Runix FS change the data in my bucket?

In cache mode, no: paths map one to one to object keys and writes pass through to the bucket. In file-system mode, writes complete in the cluster first and reach the bucket through a background sync.
